# 複数人で開発するときは、持ち主の承認を必須にする

- 日付: 2026-10-23
- 状態: stable

## 背景

[PDR-0009](./pdr-0009-codeowners-example.md)は、`.github/CODEOWNERS.example`でパスごとの持ち主を決め、決定の記録の置き場を記録の種別を決める人に持たせた。[META-05](../00-meta/dev-flow.md)の「複数人で開発するとき」は、mainの保護に4つの設定（PRを必須にする、承認1人以上、必須のチェック、force pushの禁止）を挙げていた（setopic/game-template#38）。

GitHubのmainの保護には、「Require review from Code Owners」の設定もある。無効のままだと、`CODEOWNERS`は持ち主をレビュアーに付けるだけで、持ち主でない人の承認1つでもマージできる。有効にすると、持ち主のパスを変えるPRは、その持ち主が承認するまでマージできない。

GitHubでは、PRを出した人は自分のPRを承認できない。1つの行に持ち主を2人以上書くと、どちらか1人の承認で足りる。

## 決定

複数人で開発するときは、mainの保護で「Require review from Code Owners」を有効にする。META-05の「mainを保護する」の表に、この設定を足す。

役割が1人だけなら、その役割の行に代わりの持ち主を並べる。持ち主が自分のパスを変えるPRを出しても、代わりの持ち主が承認できる。誰を代わりにするかは、作品の人の構成で決まるので、テンプレートは決めない。`CODEOWNERS.example`の行は変えず、冒頭の注記とMETA-05の「持ち主を決める」に、このやり方を書く。

## 理由

PDR-0009が持ち主を決めたのは、DDRや`project.godot`のように、決める人が決まっているパスを、その人に見てもらうためである。承認を必須にしないと、持ち主はレビュアーに付くだけで、ほかの人の承認でマージできてしまう。

代わりの持ち主を同じ行に並べるやり方は、GitHubの`CODEOWNERS`の書き方だけで済む。mainの保護を抜ける道を作らないので、必須のチェックも残る。

## 却下した案

| 案 | 却下理由 |
| --- | --- |
| 持ち主の承認を必須にしない | 持ち主がレビュアーに付くだけになり、PDR-0009で持ち主を決めた意味が薄くなる |
| 必須にするかを作品に選ばせる | テンプレートとしての既定値が無くなる。作品ごとに同じことを考え直すことになる |
| 持ち主をチーム（`@org/team`）で書き、各チームに2人以上を入れることを条件にする | 少人数の作品では、役割ごとに2人をそろえられないことが多い |
| テンプレートの管理者に、ルールセットのbypassで保護を抜けさせる | bypassはそのルールセットの全部を抜けるので、必須のチェックを別のルールセットに分ける必要がある。抜けたことがPRの上で目立たない |
| 各行に`@<代わりの持ち主>`を書いておく | 役割が2人以上いる作品では、消す手間が増える。誰を代わりにするかは、作品の人の構成で決まる |

## 影響

複数人で開発する作品は、mainの保護に設定が1つ増える。役割が1人だけの作品は、`.github/CODEOWNERS`を書くときに代わりの持ち主を並べる。

1人で開発する作品には当たらない。META-05の「複数人で開発するとき」は1人のあいだは当てず、PDR-0009のとおり`.github/CODEOWNERS`も作らなくてよい。1人のときにmainの保護を設定すると、「承認1人以上」の設定だけで、自分のPRをマージできなくなる。

## 見直しの条件

持ち主の承認を待つあいだにPRが止まることが多いとき。GitHubが、PRを出した人の承認の扱いや、持ち主の承認の設定を変えたとき。
